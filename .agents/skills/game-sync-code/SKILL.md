# game-sync 编码与架构

本技能适用于每一次代码编写任务，不需要用户另外要求“架构评审”或“设计评审”。全项目目标、架构约束、资源、配置、坐标、验证及 Git 规则由仓库根目录 AGENTS.md 维护；本技能提供编码流程与设计检查，不与之重复冲突。开始改代码前先读取本技能和适用的 AGENTS.md，再根据改动范围阅读 PROJECT_STATUS.md 及相关状态文档。

## 每次编码任务的流程

1. 确认用户要解决的问题、范围、验收结果和禁止事项；检查当前分支、工作区现有改动，避免覆盖用户内容。
2. 阅读相关模块和真实调用链，确认已有实现、数据所有者、生命周期和项目依赖；目录名本身不能证明职责归属。
3. 编码前做简短设计检查：职责是否按业务能力归属、状态是否只有一个所有者、依赖方向是否正确、失败/取消/断线/重启时谁清理、资源是否有上限、协议或持久化契约如何兼容。发现边界问题时在实现中一并修正，不为形式化评审另生成报告。
4. 选能满足当前需求的最小结构，复用项目已有类型和库；不要仅为套用模式引入接口、容器、服务层、依赖注入、微服务或通用框架。
5. 实现后检查完整 diff、调用方、资源/序列化引用和失败路径；运行与本次改动匹配的现有构建、检查或实际验证，并按 AGENTS.md 更新状态文档。清楚区分代码编译、Unity 导入、Editor/Player 运行和设备实测；未执行的验证标为待完成。

## 生成流程

1. 读取仓库与目标目录的 AGENTS.md，并结合 PROJECT_STATUS.md、相关状态文档确认现有实现、接口及本次任务范围。
2. 根据项目职责边界确定文件位置与协作关系，复用现有实现，按下面的写法生成代码。
3. 涉及自动生成文件时，先读对应工具说明，修改脚本或模板后运行生成器，不手改生成产物；核对生成器与产物一致。
4. 复核调用方、资源绑定和失败/退出路径；按 AGENTS.md 执行匹配改动的验证与文档更新，只报告实际完成的结果。

## 命名与注释

- C# 私有成员变量（含静态和只读字段）使用 m_ 加大驼峰，例如 m_UnitViews、m_Instance；所有成员变量需有中文用途注释，优先使用字段上方的 XML summary。
- public 类型、方法、属性、常量和枚举成员使用 PascalCase；参数与局部变量使用 camelCase，不加成员变量前缀。
- 不在业务代码中散落含义不清的数字或字符串字面量。协议版本、容量/长度限制、超时、阶段号、数组位置、状态码和有业务意义的固定值应提取为具名常量或枚举；调用点使用名称后仍需能看清语义。零值哨兵、常规循环索引和显而易见的算术常量不为形式而命名；共享契约值优先从其唯一来源读取，避免重复定义。
- 新增或修改的行注释、块注释、XML 文档注释统一使用中文，第三方原始文本保持原样。注释解释用途、数据含义或生命周期，不逐行复述显然行为。
- 工具生成的 C# 字段和注释同样遵守这些规则；Excel/二进制原字段名按项目配置约定保留。

## 函数文档与关键流程注释

- 面向不了解当前模块或库的项目维护者编写注释。新增或修改的公共类型、构造函数、方法和属性使用 XML 文档；私有方法和 Unity/第三方回调在用途或调用时机不直观时同样补充说明。不要只在函数开头堆一段总说明。
- 用 `<summary>` 说明职责与结果；有参数时用与签名逐一对应的 `<param name="...">` 说明语义，而非重复类型或变量名。涉及坐标/方向/时间时写明坐标系、单位、范围；涉及空值、布尔开关、引用资源时说明可空性、两种取值的影响、所有权或生命周期等实际约束。
- 非 void 返回值使用 `<returns>` 解释含义，特别是 false/null、默认值、失败与取消、查询未命中、消费后清空等行为；异步方法说明等待完成的结果。影响调用方的限制和副作用可放 `<remarks>`；实际会向外传播且调用者需要知道的异常使用 `<exception>`，不要虚构兜底或异常保证。
- 函数头文档不能代替实现过程注释。新增或实质重写的多阶段方法，应在方法体内按阶段说明该段处理什么输入、产生什么状态/结果，以及阶段之间的推进条件；不能只在方法声明上方放一段总述。
- 有业务判断、状态切换、提前返回、重试、缓存、回调或清理的代码段，若读者需要结合上下文才能知道“为什么这样分支、跳过或排序”，就在该段之前用独立成行的 `//` 解释原因和错误做法的后果。简短、直观的单行校验无需强行配注释。
- 对包含多个实质逻辑块的方法，逐块检查是否交代了其职责和与相邻步骤的关系；复杂流程允许连续写两三行注释讲清协议/玩法规则、状态变化和下一步条件。目标是读者能顺着方法体理解流程，不要求固定注释行数，也不在每条语句旁翻译代码。
- 关键流程、非显然分支和第三方 API 调用附近的注释，应解释采用该顺序、约束或方案的原因，以及省略后可能发生的问题。重点覆盖资源复制与释放、事件订阅/退订、异步取消、状态切换、输入边沿缓存、坐标转换、协议兼容、请求幂等和回调重入；按逻辑块说明，不机械地给每行加注释。
- 对项目首次接入或读者不熟悉的库，在实际调用处简要解释 API 的作用，以及它如何关联配置、数据流或生命周期。例如输入动作、触发回调、虚拟设备与 UI 事件的关系。完整教程和重复背景放相关说明文档，代码保留理解该段所必需的上下文。
- 注释不能代替清晰命名和简单结构，也不能仅把代码翻译成中文。避免“设置变量”“调用方法”等无信息注释；采用完整、准确的中文句子，`//` 后留空格，长说明分行，不把注释挤在代码行尾。
- 写注释前确认读者无法仅凭命名、类型、结构、测试或邻近文档恢复该信息；优先说明业务动机、隐含契约、边界条件和变更风险，不复述显而易见的赋值、校验或循环。涉及外部限制、性能、安全或兼容性的解释必须能由项目代码、官方 API 文档、协议或项目文档佐证，不能猜测原因。
- 注释应描述代码当前长期成立的约束，不记录“本次修改”“之前做法”或对评审者说的话。检查注释是否紧邻其解释的代码、是否仍准确；若实现、参数或时序改变，同步修订或删除失效说明。不要用注释掉的旧代码代替版本历史。
- 修改实现、参数或时序时同步核对注释；明确事实、前提与尚未实现的内容，不能把预期或未验证行为写成保证。删除过时、误导或大段注释掉的旧代码，历史由 Git 保存。
- 生成流程的复核同时检查：参数语义是否足够、返回/失败行为是否清楚、方法体中的关键逻辑块是否逐段可理解、分支原因及后续状态影响是否说明，以及初次接触相关库的读者能否沿调用链理解。若新增复杂方法只有函数头注释、没有方法体内的阶段或决策说明，视为注释复核未完成。只补全当前任务涉及的代码，不为满足格式批量改写无关历史文件。

## 代码写法

- Unity 中可在编辑状态一次配置、运行期间稳定不变的组件和引用，优先放在场景或 Prefab 的 Inspector 中绑定，例如 EventSystem 的输入模块及动作引用。代码负责动态数据、生命周期和确有必要的运行时创建；不要为固定配置重复添加自动查找、创建、绑定和失败兜底流程。接入后核对序列化引用并说明动态创建的实际原因。
- 优先使用 using 和简洁类型名。只有真实命名冲突才使用别名或类型全名；生成字段遮蔽枚举类型时才保留必要的 global::。
- 非必要不使用嵌套类或额外数据容器；配置字典与只读列表直接作为配置类成员，不额外引入 State 包装类。
- 按项目单例约定生成派生类时，使用私有无参构造，通过 Instance 获取，避免重复维护实例字段。
- 配置加载清单采用自动生成的 partial 实现，手写入口保留可扩展逻辑；不得让每次生成覆盖用户维护的管理器实现。
- 重命名序列化字段时使用 FormerlySerializedAs 或明确迁移现有资产；处理取消、失败和释放后继续执行的路径，避免生成只覆盖成功流程的代码。

## 职责边界与设计

- 按业务能力组织目录和命名空间，保持模块内聚、减少无关依赖；不能只按技术实现或文件类型归类。玩法状态和玩法规则放在 Gameplay/Room 等玩法域目录；Network 负责连接、协议校验、协议与玩法请求之间的转换及网络回包，不拥有玩法状态。
- 保持依赖方向清楚：玩法域不依赖 LiteNetLib、Protobuf 消息类、Unity 表现对象或具体传输实现。网络边界把生成协议 DTO 转成玩法层输入，并把玩法结果映射回协议 DTO。
- 为每份可变状态明确唯一事实来源。Session 只保存连接、握手和会话请求状态；RoomManager 独立拥有房间、成员、准备和开始状态，断线清理通过明确的玩法接口调用。避免在多个层维护容易分叉的重复状态。
- 普通管理器按 AGENTS.md 约定复用 shared/Runtime/Singleton<T>；派生类 sealed、私有无参构造，经 Instance 访问。只有生命周期明确属于单次调用或可替换实例的服务，才作为普通对象注入。
- 新增 Manager 前先确认它管理的业务状态、生命周期与调用边界；避免把相邻职责塞入已有 Manager，也避免仅为包装一次调用增加抽象层、接口或数据容器。
- 网络、配置和序列化等外部边界要明确输入校验、消息方向、授权依据、大小/数量限制、版本兼容和错误语义；不得信任客户端自报的权威身份或状态。
- 队列、缓存、重试和异步任务必须有明确上限或退出条件；重试需考虑幂等，关闭、断线、取消及重启时释放归属资源并阻止旧回调污染新生命周期。
- 关键操作应可诊断：复用项目日志约定，必要时记录关联 ID、失败原因和资源/耗时指标；避免记录密钥、完整敏感数据或每包重复日志。
- 对外接口、Protobuf 字段和配置格式按契约演进；新增字段不复用已占用编号，破坏性修改检查所有调用方并明确迁移或版本边界。
- 设计检查以职责内聚、低耦合、状态所有权、生命周期、资源边界、失败恢复、安全校验、可观测性、接口演进和可验证性为重点；只指出有代码或需求证据支持的问题，不要求当前小项目预先具备横向扩展、多租户、多地域、微服务或云部署方案。
- 可测试性通过清晰边界、确定性输入和可观察结果保持；新增测试代码仍受 AGENTS.md 的授权约束，不能为增加覆盖率而擅自扩展任务。

## 异常处理与兜底

- 在明确的模块或业务处理边界捕获异常，记录一次 Error，并执行清理、回滚、中止或返回失败等兜底；已处理的异常不再向外抛出。
- 调用方必须能够识别失败。查询未命中、校验不通过等预期失败优先使用 bool、Try 方法或明确返回结果，不通过异常控制正常业务流程。
- 底层允许抛出无法继续执行的异常，由处理边界统一捕获；不要每层重复捕获或重复打印同一个错误。
- 禁止吞异常、假装成功，或用默认值掩盖无效状态。配置加载失败保留旧配置，首次失败中止初始化；创建失败清理半成品并且不登记到管理器。
- 取消操作按正常生命周期处理，按实际需要清理，不把退出取消当作业务错误。日志后端自身失败不得递归记录而引发新的业务异常。

## 日志

- 运行时代码、Editor 工具和服务端统一通过 `GameSync.Logging.Log` 输出；不直接调用 `Debug.Log*` 或 `Console.WriteLine` 记录业务日志。
- 每条日志必须显示调用类与函数，统一使用 `Log` 自动采集的调用源信息，格式为 `[时间][级别][类名.函数名] 消息`。不要在消息正文中重复拼接类名或函数名。
- 记录异常时通过 `Log.Error(消息, exception)` 保留调用源和异常堆栈；同一异常只在负责处理的边界记录一次。
- `Debug.Log*` 与 `Console.WriteLine` 仅用于日志后端实现，或启动共享日志前不可避免的最早期故障输出。
