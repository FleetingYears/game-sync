# 公共网络层实施计划

状态：N0 Windows 本机门槛已完成；独立 Player/手机与 N1～N5 待实施。最后更新：2026-10-16。

## 1. 目标与已确定的方向

为 Unity 2022.3 客户端和 .NET 10 服务端建立可共同使用的网络基础，同时支撑状态同步和帧同步。保留商业项目中清晰分层、成熟依赖和可验证边界的原则，当前范围收敛为同一 Wi-Fi/局域网内的双人对局，不预建分布式大厅、微服务或通用 RPC 框架。

确定采用独立 C# 服务端拓扑、成熟 UDP 网络库、Protobuf 业务消息与按消息选择交付保证。网络库负责 Socket 收发、传输连接、确认、重传、排序和分片等能力；项目只做薄适配并使用库的接口。业务消息通过 .proto 定义和 protoc 生成编解码，不自行再写一套可靠 UDP 或逐字段业务编解码。

当前服务端只支持并验收 Windows，运行在本地电脑上；客户端按实际持有的 Windows 电脑和手机设备验证。至少用两台真实设备验证同一房间，手机平台只验收现有设备可执行的构建与运行。Android/iOS 未测平台不能记为通过；Linux 因暂无设备移出本轮，浏览器、主机平台也不属于本轮目标。

首轮不部署公网服务器，不建设账号服务、证书体系、NAT 穿透、中继或云基础设施。局域网版本仍保留协议与房间校验、资源上限、异常清理和基本统计；公网安全及其他平台作为未来独立扩展，不阻塞当前局域网验收。

### 局域网连接方式

- 一台 Windows 电脑运行 server；同一电脑可以同时运行一个客户端，另一客户端运行在同一 Wi-Fi 的另一台电脑或手机。两台手机同时连接电脑服务端也属于支持目标，按现有设备验收。
- 服务端监听可供局域网访问的网卡地址或明确配置的监听地址，并显示可连接的局域网 IPv4 与 UDP 端口；客户端先手动输入/配置此地址。其他设备不能使用 localhost/127.0.0.1 连接这台电脑。
- 客户端和服务端不写死开发机 IP。客户端通过 Inspector 默认配置和连接界面提供地址，服务端通过配置/命令行提供监听端口；局域网自动发现只在实际需要时另加。
- 验收记录 Windows 防火墙入站 UDP 规则、Wi-Fi 名称/子网和所用地址。访客网络或 AP 客户端隔离可能阻止设备互通，同一 Wi-Fi 名称不自动证明可达；先验证实际网络配置，不用公网端口映射解决局域网问题。
- N3 的跨设备收发/房间验收与 N5 的真实对局分别记录。能够连接、加入房间或 Echo 往返，不等于角色交互和同步方案已经完成。

## 2. 传输库选型及准入条件

阶段 N0 优先验证 LiteNetLib 2.x 的固定稳定版本：其官方资料列出 .NET Standard 2.1、Unity 支持以及多种可靠/非可靠交付方式，纯 C# 集成方向适合当前双端工程。官方建议 Unity 使用源码或源码包；实际版本、源码所需语言级别和 IL2CPP 兼容性仍须验证，不能仅凭目标框架判断通过。[LiteNetLib 官方说明](https://github.com/RevenantX/LiteNetLib)

当前优先验证 LiteNetLib，不为公网能力同时引入更复杂的替代方案。如果它无法满足当前 Windows/现有手机的实际兼容性、可靠性或资源约束，再评估替代库。GameNetworkingSockets 的可靠/不可靠消息、加密与多消息流能力留作后续选型参考，本轮不实施其原生构建、证书或公网集成。[Valve 官方说明](https://github.com/ValveSoftware/GameNetworkingSockets)

不同时引入两个库。用最小收发验证完成选型后，只保留一个适配器与一份依赖锁定记录，记录版本/提交、许可证、引入方式、已验平台及升级步骤。候选库至少满足：

- 客户端与服务端能够用相同版本、相同通道定义通信；共享接口仍兼容 netstandard2.1/C# 7.3，无 Unity 引用。
- 优先验证当前需要的可靠有序和不可靠交付；可靠无序及按序淘汰旧数据在消息需要时准确映射。无法提供的能力明确拒绝，不能悄悄改成另一种语义，也不为尚未使用的组合预建实现。
- 能限制连接数、消息大小、排队数据和发送速率，能观测 RTT、重传、丢弃与断线原因；识别库内部是否存在无界缓存。
- 区分独立排序域与共享连接带宽。不同通道不能被描述为绝对互不影响，必须验证大消息对实时消息的影响。
- 记录库的安全能力及当前局域网版本的限制，不能将 CRC 或连接字符串当成身份认证/加密。不为本轮引入公网密码握手；需要公网能力时单独重新评估安全方案。
- 依赖源代码单独放置和编译，不将第三方代码直接混入 shared/Runtime 的 C# 7.3 编译范围，不把产物 DLL 放回 shared 源码包。

N0 同时验证并锁定兼容的 protoc 与 Google.Protobuf 版本，检查生成代码及运行库在 shared 的 netstandard2.1/C# 7.3 和实际 Unity 构建中的兼容性。N0 产出一个传输库、一个 Protobuf 工具链的依赖锁定记录；未测平台保持“待验证”，本轮不做公网准入结论。

## 3. 分层、组织与调用方向

以下是拟定位置，实施时按实际职责创建文件，不预先生成空类。

- shared/Runtime/Network：传输接口、连接标识、交付语义、收发结果、关闭原因和统计定义。保持薄接口，不泄露第三方 Peer、Socket 或 Unity 对象。
- shared/Runtime/Protocol：消息编号、必要封套、Protobuf 解析器注册、基础会话消息的派发与业务校验；不手写 Protobuf 字段解析。共用 ID、Tick 等基础类型放共享基础；两种方案专属消息分别放各自 StateSync/FrameSync 目录。
- 第三方传输适配器：独立程序集/项目供两端使用，只依赖网络公共契约，封装库的初始化、服务轮询、通道映射和资源回收。具体目录在 N0 确认引入方式后确定。
- client/Assets/Scripts/Logic/Network：客户端连接与会话流程。Bootstrap 绑定静态配置，Application 管理连接和退出，网络事件在主线程消费；View 只显示状态。
- server/Shared/Network：监听、连接登记、会话验证、公共消息派发、基础双人房间和退出清理。
- client/server/shared 各自的 StateSync、FrameSync：输入与业务帧消息、快照/组帧、恢复策略。只依赖公共层，不能互相引用，公共网络不引用任何方案实现。

最小接口需要表达 Start/Listen、Connect、Send、Poll/Drain、Disconnect、Stop 和统计读取；它们调用成熟库提供的能力，不另写 Socket 收发、ACK、重传、排序或分片算法。不为只有一个实现的内部细节继续增加抽象。Send 结果区分本地接受入队、未连接、长度非法、受限和队列满。入队成功不等于远端已经执行。

固定端口、超时、队列上限等在客户端 Inspector 配置资产和服务端配置/命令行中提供；可变的局域网 IP 允许用户修改，公用协议限制双方一致。首轮不要求账号凭据；后续若引入机密信息，由运行环境注入，不进入场景、源码或公开仓库。

## 4. 消息交付策略

公共层提供明确的交付语义与逻辑通道，第三方适配器映射到实际能力。首次只开放用到的组合。

- 控制通道：可靠有序，承载握手、加入/离开、准备与开始。加入请求带 RequestId，服务端为可重复请求提供幂等响应；传输层可靠不能替代业务幂等。
- 高频状态通道：不可靠按序，适用于能够独立解码、可被更新数据替代的完整状态。发送端合并未发出的旧状态，接收端依据业务版本/Tick 丢弃旧数据。
- 输入通道：按方案选用可靠有序，或带有限历史冗余的不可靠消息。选择和参数由方案记录，不能由公共网络假定所有输入可丢弃。
- 恢复通道：可靠交付，用于基线、缺帧补齐等恢复请求/响应。大内容采用有总量上限、校验和取消条件的分块；不与开始游戏控制消息共用同一个排序队列。
- 探测信息：优先使用库的心跳/RTT 统计。确需自定义时间同步时使用带序号的轻量消息，不重复叠加另一套可靠性算法。

业务消息类型注册时固定合法方向、通道、交付方式、最大大小与合法会话状态。拒绝客户端发送服务器专属消息或用低优先级通道绕过限制。通道划分不表示可跨通道假设到达顺序；创建、销毁与快照之间用实体代次/业务 Tick 等显式关联，由同步方案定义。

按序淘汰必须先确定排序域。例如同一通道发送每帧完整批次快照可按批次淘汰；分别更新不同实体的消息，不能因后一个实体的更新到达，就把前一个实体尚未到达的更新当作过时数据。库不提供所需排序域时，使用不可靠交付并由方案层按实体版本筛选。

## 5. 协议、边界及带宽预算

V1 业务消息使用 Protobuf：在 .proto 中定义字段，由 protoc 生成 C# 类型及编码/解析逻辑，运行时使用 Google.Protobuf。握手、Echo、房间请求、输入、快照、组帧和补帧等都先采用该方式，不先手写一批消息再迁移。[Protobuf 官方 C# 教程](https://protobuf.dev/getting-started/csharptutorial/)

拟定组织：protocol/Common 存放公共 .proto，protocol/StateSync、protocol/FrameSync 分别存放方案专属定义；tools/ProtocolGenerator 提供固定版本的可重复生成入口。公共生成代码只保留一份，拟放 shared/Runtime/Gen/Protocol；方案专属产物位于对应 StateSync/FrameSync 范围内，不能为客户端/服务端各生成同名类型后同时编译。实际接入时核对官方生成代码的格式与项目技能约定，明确工具产物边界，不手改生成文件或复制修改第三方生成器。

protoc 与运行库版本一并锁定，不依赖开发机 PATH 中恰好安装的版本；保留生成文件已有 .meta/GUID。字段编号一经使用不复用，删除字段保留 reserved，兼容变更和破坏性变更分别记录。共享生成类保持无 Unity 依赖；没有 AOT/IL2CPP 实测就不宣称移动端通过。[版本兼容规则](https://protobuf.dev/support/cross-version-runtime-guarantee/)

公共消息封套包括协议主版本、消息类型、负载长度；需要请求关联的消息携带 RequestId。封套是否也用 Protobuf 或少量固定头，在 N0/N2 统一确定；手写范围仅限必要封套与类型派发，不重复实现业务消息序列化。玩家身份取自服务端分配的局域网会话上下文，不能相信负载中自报的 PlayerId；当前没有正式账号认证。传输包序号、请求号、输入序号、逻辑 Tick 和实体 ID 是不同概念，不复用一个字段。

UDP/库已经保留消息边界，不套用 TCP 的接收流拆包方案。解析前检查版本、会话状态、类型、总长度和速率，并在 Protobuf 解析器支持范围内限制大小/嵌套深度；解析后校验字符串长度、repeated 元素数量、数值范围和房间成员资格。Protobuf 能解析不等于业务合法，也不能在解析后才限制整个包的大小。未知主版本拒绝连接，未知消息按协议明确拒绝或忽略，不能进入错误处理循环。

高频输入和快照先用 Protobuf，记录消息体积、序列化耗时与分配；只有实测预算不足时再单独设计量化、增量或位打包。Protobuf 不决定帧同步的目标帧、缺帧与回滚策略，也不自动提供确定性；不得直接把它的序列化字节当作跨实现稳定的逻辑状态哈希格式。[Protobuf 非规范化序列化说明](https://protobuf.dev/programming-guides/serialization-not-canonical/)

MTU 预算区分 IP/UDP 头、库头、加密标签与应用负载。以约 1200 字节 UDP 负载作为初始保守探测预算，再扣除传输/安全封装得到 MaxAppMessageBytes；最终值由候选库和路径验证确定，不把“1200 字节业务消息”当成保证不分片。高频消息必须控制在已验证预算内；可靠分片即使库支持，也只用于有界恢复等低频消息。

每连接和全局均限制消息数、字节数、排队时长、未完成握手的连接与分块重组总量。可靠消息队列满时返回失败、减速或按策略断开，不能无限排队或静默丢弃；允许淘汰的状态消息按类型/实体覆盖。传输库负责其重传和拥塞机制，应用层仍需预算流量、限制突发并降低快照/恢复频率。

不在当前本地 float 输入或网络解码器中擅自确定帧同步数学。状态同步的量化规则、帧同步的定点输入和状态哈希格式分别在计划 5、4/6 中定义。

## 6. 连接与会话生命周期

客户端流程：Disconnected → Connecting → TransportConnected → Handshaking → Ready → InRoom → Closing → Disconnected。连接行为由传输库提供，应用握手检查协议与开发会话信息；传输连接建立不代表已加入房间或可以提交输入。每次连接生成新的本地连接代次，异步回调与队列事件带代次，关闭后迟到事件不能驱动新会话。

服务端在准入、版本和基本会话检查通过后分配 Session/Player，加入房间后再允许玩法消息。局域网首版使用临时玩家标识/显示名，不实现账号登录；不同客户端由连接与 Session 区分，不能只按 IP 区分。房间准备状态确认后广播开始标识；只有专属同步方案设置逻辑开始帧与输入时序。

配置初始建议值：连接/应用握手阶段各 5 秒超时，心跳空闲探测约 1 秒、失活判定约 10 秒。这些是 N1 的可调起点，不是已测结论；移动端暂停和传输库自身超时需一起验证，避免多套计时器矛盾。

第一版明确不提供无缝断线续局。超时、切后台导致连接失效或服务端重启后，先关闭旧会话并释放房间资格；重试受退避、次数和用户操作约束，按新会话重新握手、加入房间。旧可靠队列不可自动重放到新会话。断线恢复阶段以后再确定保留玩家槽位、补状态/补输入的有效窗口。

时间使用单调时钟测量间隔和 RTT，暂停后的时钟跳变要处理；逻辑 Tick 不等于系统时钟。连接/心跳可在玩法开始前运行，不因等待确定性数学而阻塞网络基础实施。

## 7. 线程、事件与内存所有权

第一版采用显式轮询派发：Unity Update 处理有数量和耗时预算的网络事件，服务器主循环独立服务网络；收到的数据先进入会话/输入缓冲，模拟 Tick 只消费已排定的业务数据。渲染帧率不决定模拟 Tick。

优先使用库的 PollEvents 等机制将回调交给指定线程。库内部接收线程不得访问 Unity 对象、修改房间或直接推进模拟。如果必须跨线程入队，队列有界，事件携带连接代次和收到时间，并明确缓冲区复制、租借与归还责任。

不在网络回调中创建/销毁外观、播放特效或加载资源。解码后的数据在主线程/服务器业务边界派发；同步适配器再决定如何驱动模拟及公共表现。处理异常记录一次上下文并执行丢弃、拒绝或关闭，错误日志按原因采样，避免畸形包引发日志洪泛。

关闭时停止接收新业务、取消连接等待、退订回调、排空或丢弃旧事件并回收缓冲区，最后释放传输对象。重复关闭须幂等；单个房间退出不销毁其他房间仍在使用的公共监听器。

## 8. 当前局域网边界、观测与后续扩展

局域网首版保留连接/房间容量限制、握手超时、消息方向与状态校验、基础速率限制和非法数据处理。静态 connection key 如使用，只作协议筛选，不充当密码或账号认证；不因是同一 Wi-Fi 就放弃校验或资源上限。

正式账号/短期凭证、服务器身份验证、认证加密、防重放、抗反射与 DDoS 防护、NAT 穿透/中继、云部署和运维均为以后明确扩大到公网时的独立工作，本轮不实施也不作为 N0～N5 的验收门槛。Linux 服务端及没有实际设备的平台同样后置。

最少观测项为：连接/握手成功率与耗时、活跃连接/房间数、RTT 及其波动、收发字节/消息数、重传与丢弃、排队字节/时长、解析拒绝、超时/断线原因、事件派发耗时及 Protobuf 序列化分配。记录库统计的准确含义与时间窗口，不把 Ping 当成用户完整操作延迟。

日志通过现有 Log 输出，只保留必要的 Session/Room/Request 等关联信息，不打印凭证、密钥或完整包体。开发 HUD 展示连接状态、RTT、流量和队列压力；后续的校正、回滚次数由各方案补充，不混进传输协议。

## 9. 状态同步与帧同步的专属部分

状态同步（计划 5）负责输入确认、快照 Tick、实体代次、基线与增量依赖、插值、预测校正和兴趣管理的实际需要。增量快照不能一律“只收最新”：缺少基线时必须等待、丢弃并请求恢复，按协议处理。可靠通道也不能解决跨通道的生成/快照竞态。

帧同步（计划 6）负责目标帧、输入集合、组帧截止时间、迟到输入、补帧、预测/回滚和哈希。必要输入最终需要补齐或被明确的超时规则替代，不能因为使用不可靠通道就忽略缺帧。基础锁步先用可靠交付建立正确性，再根据 N0/N4 结果决定是否改用输入冗余和业务确认；不默认可靠有序就是最终低延迟方案。

传输库的包去重与排序不等于业务帧缓冲、业务幂等或回滚事件去重。公共层不理解 Snapshot、FrameInput，不引用两种方案类型；两种方案可以选择不同通道策略，但不能各复制一套连接和资源生命周期代码。

## 10. 阶段与交付门槛

N0 的 Windows Unity Editor/服务端工程探针已通过；N1～N5 未开始。下列为验收目标，实际记录见 [N0 依赖锁定与约束](NETWORK_DEPENDENCIES.md)。阶段按可独立复核的功能分支推进，公共项从 main 建 feat_common_*，合回 main 后再同步两个 dev；方案适配分别从对应 dev 建分支。

### N0：确定传输库与约束

- 使用候选库完成最小双端收发、通道能力、许可证与依赖布局验证；锁定一个稳定版本，不依赖 master 最新源码。不新增自己的 Socket/可靠 UDP 实现。
- 验证固定 protoc/Google.Protobuf 工具链，生成并往返解析最小业务消息；确认双方共享同一份定义与兼容的生成代码，不手写业务字段编解码。
- 在实际 Unity 中刷新、编译、运行，先完成 Windows 客户端/服务端收发；现有手机所需构建能力记录在案。Linux 和没有设备的平台不设为首轮门槛。
- 确定消息预算、队列上限、线程模型与统计读取方式，输出适用于本轮局域网范围的选型决定。
- 拟用分支：feat_common_network_transport。

### N1：最小可靠通信与生命周期

- 薄封装库的监听、连接、发送、轮询与关闭接口；接入 Protobuf 版本握手和 Echo/探测，明确入队结果、关闭原因、取消及超时。
- 两个客户端独立连接；可靠/不可靠消息均能收发；主线程派发有预算；反复启停不保留旧会话或回调。
- 验证连接拒绝、服务端不可达、进程被终止、网络恢复、消息过大与队列满，不能无界重试。
- 拟用分支：feat_common_network_session。

### N2：公共协议与双人房间

- 编写公共 .proto 并生成业务消息编解码，接入有界解析、类型注册、消息方向/会话状态校验，以及加入、退出、准备、开始流程。
- 实现请求幂等、版本不兼容拒绝与临时会话玩家分配；未完成握手的客户端不能加入房间，非房间成员不能提交输入。本轮不依赖正式账号认证。
- 验证重复加入、第三人进入满房、重复开始、房间退出、客户端伪造消息和服务端清理。
- 拟用分支：feat_common_network_room。

### N3：同一 Wi-Fi 的多设备验证

- Windows 电脑启动服务端，至少两台实际设备上的客户端连接同一局域网 IP/端口，完成消息往返、加入、准备、开始和退出。不能只用同机两个进程代替此项。
- 验证可修改的局域网地址/端口、Windows 防火墙入站规则、访客/AP 隔离问题的提示；不部署云服务器，不配置公网端口映射。
- 在实际持有的手机平台构建运行，按该平台实际后端检查 IL2CPP 兼容、暂停/恢复、断开 Wi-Fi 和重新加入。没有设备的平台保持未验状态，不阻塞已经验证的目标组合。
- 资源后端尚未完成时可先验证独立网络模块，但完整手机游戏的启动/资源加载仍是 N5 对局验收依赖，不得把收发成功当作完成游戏。
- 拟用分支：feat_common_network_lan。

### N4：故障、负载与可观测性验收

- 从 N1 开始使用固定种子的扰动配置，优先用现有库模拟或外部网络工具，不叠加两套不明来源的扰动。
- 单向额外延迟基线：0 毫秒；常见环境：50 毫秒、抖动 ±10 毫秒、丢包 1%；较差环境：150 毫秒、抖动 ±40 毫秒、丢包 5%、乱序/重复各 1%。记录影响方向、分布、突发模型及测得 RTT；数值是初始验收样本，不是行业承诺。
- 注入约 3 秒短暂中断和超过配置失活阈值的中断；验证恢复或按规则断线、旧会话拒绝、缓存回收。可靠消息的交付保证只适用于连接有效且未超过资源/超时约束的区间。
- 双客户端至少运行 60 分钟，另做连接数/消息速率超限验证；队列保持在配置上限内，无持续缓存增长，控制消息不被恢复数据长期挤占。记录 CPU、分配、内存、句柄、流量与失败原因。
- 形成可复现记录，不以“没报错”替代预算指标；实施前冻结各项预算与阈值，再按结果调参并保留版本。
- 拟用分支：feat_common_network_validation。

### N5：分别接入两种同步方案

- 计划 5：从 dev_state_sync 创建 feat_state_network_adapter，接入快照与输入确认；测量延迟、带宽和状态收敛。
- 计划 6：从 dev_frame_sync 创建 feat_frame_network_adapter，接入输入组帧、缺帧恢复；依赖计划 4 确定性数学与模拟，测量一致性、输入等待和回滚。
- 复用相同网络基础、扰动参数与玩法场景做计划 7 的对比；不得将某方案网络适配整支合入另一方案。
- 在 N3 已验证的同一 Wi-Fi 设备组合上实际完成移动、攻击及房间结束的双人对局；分别记录两种同步方案的结果。只有网络往返或房间状态成功时不勾选此项。

## 11. 当前边界与未完成项

N0 已锁定库与工具链版本、接入官方分发，并完成 Windows Unity Editor 与实际服务端工程的同机收发探针；独立 Player 与实际设备尚未验证。版本、引入方式与剩余边界见 [依赖锁定记录](NETWORK_DEPENDENCIES.md)。正式消息编号和 .proto 契约在 N2 固化，不把 N0 探针当作正式协议。

当前 shared 类库与输入/表现基础已经存在，公共协议、网络、房间、确定性模拟和同步方案尚未实现。网络 N0～N4 可先于完整玩法推进；N5 与同 Wi-Fi 真实对局必须等待相应模拟、配置和资源加载能力。公网部署、Linux、账号认证与无缝重连均不在本轮范围。

上述验收遵守仓库验证约定：本计划列出验证目标，不新增测试源码。实施时使用已有检查、构建、实际运行与外部网络工具；新增自动化测试须有用户明确要求。
