# 分支合并操作教训

本文件记录 2026-10-15 共享日志功能集成时暴露的问题及后续操作要求。执行分支合并、跨分支同步或处理“已有文件显示新增”的问题前，先复核本文件；分支隔离与推送授权仍以 AGENTS.md 和用户指令为准。

## 本次问题

玩家功能分支 feat_common_local_player 已提交代码技能，但当时尚未合入 main。日志分支从旧 main 创建，因此不包含该技能。我没有先核对文件在哪个分支，而是从本机安装目录重新写了一份，造成重复创建的疑问。

随后按“玩家功能 → main → 日志功能”同步时，main 采用快进，与玩家功能分支指向同一提交；界面显示的来源分支名称引发了对直接合并功能分支的疑问。虽然实际命令是 git merge main，但没有清晰的主线集成节点可供直观看出路径。

## 后续操作要求

1. **先查历史，再处理缺失文件。** 检查当前分支、main 和所属功能分支；使用 git log --all -- 路径、git ls-tree 分支 路径定位文件。不能因为当前分支没有文件，就从另一功能分支或本机安装目录重新创建一份。
2. **依赖先集成所属主线。** 功能 B 需要功能 A 时，在得到授权后先将 A 合回所属主线，再由主线同步到 B。禁止直接合并两个功能分支，也不能用补丁复制、cherry-pick 或 rebase 绕过隔离。
3. **主线集成来源可追溯。** 功能分支合回所属主线时，优先使用 --no-ff 保留集成节点，提交信息明确来源与功能。避免主线与原功能分支完全同指一个提交，使界面来源标签难以辨认。
4. **纯同步与新修改分开提交。** 先完成主线同步和必要冲突解决，再单独提交新增功能、规范修改或额外接口适配。不要把新写的技能规则混入同步合并提交。
5. **冲突不能简单整文件选一边。** 核对双方差异，保留有效行为；生成文件通过合并后的生成器和模板重新生成。检查调用方返回值、资源绑定、失败处理和文档，运行适当构建。
6. **修改原文件并保留来源。** 同步后应在已跟踪的文件上编辑；技能安装副本只做同步分发，不能替代仓库历史。新增规则的提交应能直接看到规则增量，而非继承文件的整份新增。
7. **说明比较基准。** 合并视图中的“新增”可能是相对第一父提交的继承变化；核对相对主线的实际增量后说明，不能只凭颜色判断，也不能只用口头解释代替证据。
8. **交付明确本地与远端状态。** 报告当前分支、合并提交、验证结果和推送状态。用户指定的操作顺序必须遵守，未授权的推送或历史重写不自行执行。
